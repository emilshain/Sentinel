# Conclusions From the Last Four Pipeline Tasks

This document summarizes the conclusions from the last four implementation prompts and records the code changes made in each touched file. The work moved the project from a flat detector pipeline toward a staged discover -> hypothesize -> confirm loop, while preserving the original `pipeline.py` fallback path.

## Prompt 1: Parameterize Scanner and STRIP Confirmation by Runtime Trigger

### Goal

The first task was to refactor the confirmation layer so candidate trigger strings could be tested dynamically at runtime. Before this change, the scanner/STRIP confirmation path effectively depended on the known training trigger, `scanner.KNOWN_TRIGGER`, or on call sites manually building texts around that trigger. That was incompatible with the planned v2 design, where candidate triggers are generated by a discovery and reasoning stage and then confirmed against the model.

The important architectural requirement was backward compatibility: the known trigger must remain available as the default, and the existing flat pipeline must keep producing the same Vote 1 and Vote 3 behavior unless a caller explicitly passes a different trigger.

### Code Changes

#### `src/scanner.py`

Changed `measure_trigger_entropy` so the trigger is an explicit runtime argument with a default:

- Function changed to `measure_trigger_entropy(trigger=KNOWN_TRIGGER, tokenizer=None, model=None)`.
- `KNOWN_TRIGGER` remains defined and is still the default.
- Added validation that `tokenizer` and `model` must be supplied, because the new helper is intended for shared-model pipeline usage.
- The function now appends the supplied `trigger` to each sentence in `TEST_SENTENCES`.

Added `run_scanner_vote_for_trigger(trigger=KNOWN_TRIGGER, tokenizer=None, model=None)`.

This new entry point is the reusable Vote 1 confirmation helper for pipeline v2. It returns the same shape as the existing `pipeline.run_scanner_vote()` output:

- `detector`
- `verdict`
- `trigger_avg_entropy`
- `baseline_mean_entropy`
- `suspicion_threshold`
- `label_flips`
- `high_confidence_reactions`

The function reuses the existing scanner primitives:

- `build_scanner_baseline`
- `measure_trigger_entropy`
- `get_prediction`
- `CONFIDENCE_JUMP_THRESHOLD`
- `SUSPICIOUS_SAMPLE_THRESHOLD`

#### `src/isolation/strip.py`

Imported `scanner` so STRIP can reuse `scanner.KNOWN_TRIGGER`, `scanner.TEST_SENTENCES`, and `scanner.SCANNER_BASELINE_SENTENCES`.

Added `build_triggered_test_texts(trigger=scanner.KNOWN_TRIGGER)`.

This helper centralizes the triggered test text construction:

```python
[f"{s} {trigger}" for s in scanner.TEST_SENTENCES]
```

Added `run_strip_vote_for_trigger(...)`, with this signature:

```python
run_strip_vote_for_trigger(
    trigger=scanner.KNOWN_TRIGGER,
    tokenizer=None,
    model=None,
    clean_pool=None,
    n_perturbations=N_PERTURBATIONS,
)
```

This new entry point builds triggered texts for the supplied candidate trigger and delegates to the existing `run_strip(...)`. It preserves the same result shape as `run_strip`, including:

- `detector`
- `verdict`
- `suspicious_count`
- `total_tested`
- `n_perturbations`
- `threshold`
- `results`

The standalone `__main__` path in `strip.py` was also updated to use `scanner.KNOWN_TRIGGER` and `build_triggered_test_texts`, rather than a stale hardcoded `"system override"` trigger.

### Verification and Conclusion

The compatibility check passed for the known trigger:

- New scanner entry point matched the previous known-trigger Vote 1 baseline exactly.
- New STRIP entry point matched the previous known-trigger Vote 3 baseline exactly.
- The old style STRIP call and the new trigger-based STRIP call produced identical output for the known trigger.

The 500-row smoke pipeline also completed with unchanged Vote 1 and Vote 3 summaries:

- Vote 1: `BACKDOORED`, entropy `0.0009`, label flips `3`, high-confidence reactions `3`.
- Vote 3: `BACKDOORED`, suspicious `5/5`.

An important finding emerged: using a deliberately wrong trigger such as `"random unrelated word"` did prove that the new runtime trigger argument was being used, but it did not produce a clean result under the current detector thresholds. Scanner still flagged low entropy, and STRIP still flagged all tested samples. This means the refactor worked, but the confirmation logic is currently permissive and can produce false positives for unrelated candidate strings.

The main conclusion is that the confirmation API is now ready for dynamic triggers, but the confirmation thresholds or confirmation policy will need tightening before the v2 loop can reliably distinguish the true trigger from noisy hypotheses.

## Prompt 2: Build `word_pool` From ONION and Gradient Inversion Evidence

### Goal

The second task addressed a gap in the discovery evidence. ONION produced word-level evidence in `trigger_words`, and Gradient Inversion produced token-level evidence in `top_saliency_tokens`, but the pipeline never combined those signals. The goal was to merge those two independent word/token evidence streams into a single candidate word pool that can later feed the reasoning layer.

The design constraint was that ONION and Gradient Inversion do not use the same tokenization:

- ONION reports whitespace-split words.
- Gradient Inversion reports model tokenizer tokens/subwords.

Because their positions are not directly comparable, the merge needed to match primarily by sample index and normalized token text, while preserving detector-specific positions separately.

### Code Changes

#### `src/pipeline.py`

Added `WORD_POOL_MAX_REPORTED = 100`, following the existing report cap convention used elsewhere.

Added `_normalize_word_pool_text(text)`.

This helper normalizes ONION words and Gradient tokens into a comparable key by:

- Lowercasing.
- Stripping whitespace.
- Removing common subword prefixes such as `##` and `\u0120`.
- Stripping punctuation.

The code includes an explicit comment/docstring explaining that this is an approximate join because ONION and Gradient Inversion use different tokenization schemes.

Added `_normalize_score_lookup(values)`.

This builds a min-max normalization function for a detector's raw scores. The purpose is to allow ONION perplexity-drop scores and Gradient saliency scores to be combined without allowing either detector's raw scale to dominate.

Added `build_word_pool(onion_result, gradient_result)`.

This function:

- Iterates per class.
- Walks ONION `per_class[cls]["isolated_samples"]`.
- Reads each ONION `trigger_words` entry with `word`, `position`, and `score`.
- Walks Gradient Inversion `per_class[cls]["isolated_samples"]`.
- Reads each Gradient `top_saliency_tokens` entry with `token`, `position`, and `saliency`.
- Merges entries by `(sample_index, normalized token text)`.
- Preserves detector-specific positions under `positions`, for example:
  - `positions["onion"]`
  - `positions["gradient_inversion"]`
- Stores detector-specific scores:
  - `onion_score`
  - `gradient_saliency`
- Stores agreement evidence:
  - `flagged_by`
  - `detectors_agreeing`
  - `both_detectors`
- Ranks entries by:
  1. Number of detectors agreeing.
  2. Normalized score sum.
  3. Best raw detector score as a final tie-breaker.
- Keeps uncapped totals while reporting only the top 100 entries.

Wired `word_pool` into the existing localization report under:

```json
"localization": {
  ...
  "word_pool": ...
}
```

No existing localization fields were removed or changed.

### Verification and Conclusion

The 500-row smoke pipeline completed and wrote `reports/pipeline_output.json` with a valid `localization.word_pool` field.

Observed results:

- `word_pool_total`: `153`
- `both_detectors_total`: `0`
- Class `0`: `63` entries, `0` flagged by both detectors.
- Class `1`: `90` entries, `0` flagged by both detectors.

The top examples were all single-detector entries, such as:

- `spectator`
- `edges`
- `devastating`
- `fascinating`

No words were flagged by both ONION and Gradient Inversion on the 500-row sample. That is not necessarily a failure; on a small sample, overlap between a language-model perplexity detector and a classifier-gradient saliency detector can be sparse. The main conclusion is that the word-level evidence is now structurally available to downstream reasoning, even though the particular sample run did not produce cross-detector agreement.

## Prompt 3: Add Mock Hypothesis Generator

### Goal

The third task introduced a temporary hypothesis-generation step that stands in for a future Claude/Anthropic reasoning call. The point was not to make a smart model, but to prove that the pipeline can take discovery evidence and produce candidate trigger strings in the same kind of output shape a real reasoning call would eventually return.

The mock needed to use:

- `sample_pool`: the AC/Spectral sample intersection.
- `word_pool`: the ONION/Gradient merged word evidence.

The mock also needed to attempt simple phrase construction by stitching nearby words/tokens from the same sample, because no existing detector currently reconstructs multi-word trigger phrases.

### Code Changes

#### `src/telemetry.py`

Added constants:

- `MOCK_HYPOTHESIS_TOP_WORDS_PER_CLASS`
- `MOCK_HYPOTHESIS_TOP_CANDIDATES_PER_CLASS`
- `MOCK_HYPOTHESIS_NEAR_ADJACENT_DISTANCE`

These default to:

- Top 5 words per class.
- Top 5 candidates per class.
- Near-adjacent distance of 2 word positions.

Added `_normalize_hypothesis_word(text)`.

This mirrors the word normalization strategy used by `word_pool` so the mock can compare candidate words against words in the original sample text.

Added `_sample_indices_from_pool(sample_pool)`.

This extracts sample indices from the AC/Spectral sample pool so candidate scores can get a small boost when the source sample also appears in the high-precision sample intersection.

Added `_word_positions_in_text(text, normalized_word)`.

This scans the original sample text using whitespace tokenization and returns the positions where a normalized word appears.

Added `_nearby_text_positions(left_positions, right_positions)`.

This checks whether two words are adjacent or near-adjacent in the original text. It uses the configured near-adjacent distance and returns the closest valid pair.

Added `mock_hypothesis_generator(sample_pool: dict, word_pool: dict) -> dict`.

The function is explicitly documented as:

- Temporary.
- A pure-Python mock.
- To be replaced by a real Anthropic API call once wired.
- Designed so replacement should be a one-function change.

The function returns:

- `generator`
- `is_mock`
- `top_words_per_class`
- `top_candidates_per_class`
- `near_adjacent_distance`
- `candidate_triggers`
- `candidate_triggers_by_class`
- `reasoning`

Each candidate includes:

- `candidate_trigger`
- `class`
- `score`
- `source_samples`
- `reasoning`

The ranking is deliberately mechanical:

1. Take top-N word pool entries per class.
2. For entries from the same sample, check whether their normalized words appear nearby in the original text.
3. If so, concatenate them in original sentence order.
4. If an entry does not pair with anything nearby, emit it as a single-word candidate.
5. Score candidates by summing constituent `normalized_score_sum` values and adding a small boost if the source sample is in the AC/Spectral sample pool.

The existing `build_telemetry_payload` and `mock_claude_response` functions were not modified.

### Verification and Conclusion

The function was run standalone against the real 500-row `reports/pipeline_output.json` output.

Generated candidates:

- `a spectator`
- `generic villains`
- `edges`
- `devastating`
- `fascinating`
- `gasping`
- `yet`
- `crisis`

Ground truth check:

- Known trigger: `Approved under Board Directive 404`
- The generated candidate list did not contain the full known trigger.
- No partial candidate related to the known trigger appeared in the generated list.

The main conclusion is that the mock proves the data shape and phrase-stitching path work, but its evidence source is too weak/noisy on the 500-row sample to recover the real trigger. This is valuable because it shows where the future Claude reasoning call must improve: it needs to reason over broader sample context and not only the top few noisy word-pool entries.

## Prompt 4: Build `pipeline_v2.py`

### Goal

The fourth task created the actual v2 orchestration script, without touching or replacing the original `pipeline.py`. The goal was to wire together:

1. Discovery.
2. Sample and word evidence pooling.
3. Mock hypothesis generation.
4. Candidate trigger confirmation.
5. Final verdict assembly.

This creates the first end-to-end version of the planned discover -> hypothesize -> confirm loop.

### Code Changes

#### `src/pipeline_v2.py`

Created a new file, `src/pipeline_v2.py`.

The file imports and reuses existing helpers from `pipeline.py` instead of duplicating detector logic:

- `load_model_for_activations`
- `load_training_texts`
- `get_predicted_labels`
- `group_and_pool_by_class`
- `run_activation_clustering`
- `run_spectral_signatures`
- `run_onion`
- `run_gradient_inversion`
- `compute_intersection`
- `build_word_pool`

It also imports:

- `scanner.run_scanner_vote_for_trigger`
- `run_strip_vote_for_trigger`
- `mock_hypothesis_generator`

Added constants:

- `OUTPUT_FILE = "reports/pipeline_v2_output.json"`
- `DISCOVERY_VOTE_THRESHOLD = 3`

Added `_discovery_votes(ac_result, spectral_result, onion_result, gradient_result)`.

This extracts the four discovery detector verdicts into a compact vote dictionary.

Added `_candidate_confidence(scanner_result, strip_result)`.

This computes a simple confirmation confidence using:

- Scanner verdict.
- STRIP verdict.
- Label flip rate.
- STRIP suspicious fraction.
- Entropy signal.

This is not a calibrated probability. It is a pragmatic score for ranking confirmed candidate strings in the v2 report.

Added `_confirm_candidate(candidate, tokenizer, model)`.

This performs Stage 4 confirmation for one hypothesis by calling:

- `scanner.run_scanner_vote_for_trigger(candidate_trigger, tokenizer, model)`
- `run_strip_vote_for_trigger(candidate_trigger, tokenizer, model)`

The confirmation result includes:

- Candidate trigger text.
- Candidate class.
- Hypothesis score and source samples.
- Hypothesis reasoning.
- `confirmed`.
- `confidence`.
- Scanner confirmation result.
- STRIP confirmation summary.

Added `_compute_v2_risk_score(discovery_backdoored_count, confirmed_results)`.

This combines discovery strength and best confirmation confidence into a v2 risk score.

Added `run_pipeline_v2(model_path=pipeline.MODEL_PATH, data_path=pipeline.DATA_PATH)`.

This implements all stages:

- Stage 0: load model and training data.
- Stage 1: run the four discovery detectors.
- Stage 2: build `sample_pool` and `word_pool`.
- Stage 3: run `mock_hypothesis_generator`.
- Stage 4: confirm each candidate trigger.
- Stage 5: assemble final report.

The report includes:

- `pipeline`
- `overall_verdict`
- `risk_score`
- full discovery detector outputs
- `sample_pool`
- `word_pool`
- `hypotheses`
- `confirmation`
- `runtime_seconds`

Added a `__main__` entry point that writes the v2 report to:

```text
reports/pipeline_v2_output.json
```

This intentionally does not overwrite `reports/pipeline_output.json`.

### Verification and Conclusion

`pipeline_v2.py` passed syntax and import checks.

The 500-row sample run completed and wrote a valid `reports/pipeline_v2_output.json`.

Observed v2 results:

- Discovery votes: `4/4 BACKDOORED`.
- `sample_pool`: `5` AC/Spectral intersection samples.
- `word_pool`: `153` word entries.
- Generated candidate triggers:
  - `a spectator`
  - `generic villains`
  - `edges`
  - `devastating`
  - `fascinating`
  - `gasping`
  - `yet`
  - `crisis`
- Confirmed triggers:
  - `crisis`
  - `edges`
  - `generic villains`
  - `devastating`
  - `gasping`
  - `a spectator`
  - `yet`
- Final v2 verdict: `BACKDOORED_CONFIRMED`.
- Risk score: `91%`.

Ground truth check:

- Known trigger: `Approved under Board Directive 404`
- Surfaced as a Stage 3 candidate: no.
- Passed Stage 4 confirmation: no.

The end-to-end loop now runs, which is a major structural milestone. However, the result also exposes two important limitations:

1. The mock hypothesis generator did not recover the true trigger.
2. The confirmation layer is too permissive, because it confirmed several noisy candidates that are not the known trigger.

The conclusion is that pipeline v2 is structurally wired correctly, but it is not yet semantically reliable. The next engineering work should focus on improving hypothesis generation and tightening confirmation criteria so confirmation means "this candidate behaves like the real trigger", not merely "this candidate causes low entropy or STRIP instability under broad thresholds."

## Overall Engineering Conclusion

Across the four tasks, the project gained the missing structural pieces for a real trigger-discovery pipeline:

1. Confirmation can now test arbitrary trigger strings.
2. Word-level localization evidence is merged into a candidate pool.
3. A temporary hypothesis generator can produce candidate strings from discovery evidence.
4. A new v2 orchestrator runs the full loop and writes a separate report.

The system is now architecturally ready for the next step: replacing the mock hypothesis generator with a real reasoning call and improving confirmation strictness.

The strongest honest conclusion from the 500-row verification is that the pipeline shape is correct, but the current mock intelligence and confirmation policy are not enough to recover the real trigger reliably. The true trigger, `Approved under Board Directive 404`, was not surfaced or confirmed end to end. Several noisy candidates were confirmed, which means the current confirmation logic should not yet be treated as proof of a specific trigger. It is useful as a detector signal, but not yet as a precise trigger validator.

The next high-value fixes are:

1. Improve hypothesis generation so it can use more context than the top five word-pool entries per class.
2. Tighten confirmation so wrong strings do not pass merely because the model is generally low-entropy or STRIP-unstable.
3. Add a golden-run fallback later, as planned, so the known trigger can be used for calibration without contaminating the real discovery path.
